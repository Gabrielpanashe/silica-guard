- **Identity resolution: a telephone number is no longer a key** (1 November 2026, branch `be/identity`, item 1.7). The second irreversible decision, and §8.2's "hardest problem in the system and the one most likely to quietly destroy the headline metric". All four parts of §8.2 are now in code and tested.
  - **The decisive assertion is a non-event.** Two brothers sharing a handset are two records. `services/ussd_handler.py:77` returns the first miner holding that number, which silently merges them; nothing in `services/identity.py` treats a number as more than one signal among several, and on its own it scores below the threshold that would even show a reviewer a candidate. Verified against real PostgreSQL as well as the unit suite.
  - **Participant codes**, six characters from the referral alphabet (no 0/O or 1/I, because a code is read aloud by a clerk and typed on a keypad). Six rather than four: about a billion codes against a million, for a register meant for more than 500,000 people where a collision mixes two clinical histories rather than confusing one hospital visit. Generation raises rather than returning a colliding code.
  - **Matching on the bundle, and nothing merged automatically.** A participant code attaches to that person. A hashed national identity number is the one deterministic match §8.2 permits and is applied. Everything else is scored and **queued for a human** — the queue is a table, with the evidence that put the pair there, because somebody has to work through it and "reviewed, and they are different people" has to survive or the same pair returns at the next screening.
  - **`resolve()` always returns a person a screening can be written against.** An uncertain identity produces a duplicate plus a queue entry, never a blocked screening. Rule 7 and §8.2 agree on which failure to prefer.
  - **Merges are reversible from the first day.** Contacts and sessions move to the winner, the winner inherits only what it was missing and overwrites nothing, the losing record is kept and flagged, and who/when/on-what-evidence is recorded. A card printed before a merge still resolves, which is the point of printing one. An unmerge restores both identities — **and deliberately does not move the encounters back**, because which rows belonged to which record beforehand is not recoverable from the surviving data; recorded in the plan (§12 item 19) rather than discovered mid-incident.
  - **The anonymous USSD case is explicit** (§8.2 part four): no participant code means a provisional identity with the reason recorded, for a health worker to resolve at the next contact. An unrecognised code on USSD is also provisional, with a different reason, rather than silently ignored.
  - **Identifiers are stored twice, hashed for lookup and encrypted for use** (`services/crypto.py`, §12 item 11). A number must be *found* — the USSD webhook arrives with a caller number — and also *sent to*, and an encrypted column cannot be indexed for equality while a hash cannot be reversed. A keyed hash rather than a per-row salt, because a per-row salt destroys the one deterministic match §8.2 relies on; the key is the salt and lives in the secret store. Every digest is domain-separated by purpose, so a number typed into the national-identity field cannot collide with the same number in the phone field and merge two people. `cryptography` is now a declared runtime dependency rather than relied on as `python-jose`'s extra.
  - **A missing key is a hard failure, not a default.** `routers/auth.py:29` falls back to `"dev-secret"` when `SECRET_KEY` is unset; that pattern is not copied. A production instance quietly hashing national identity numbers under a guessable default produces a column that looks protected, is not, and cannot be fixed afterwards. The HTTP layer turns it into a **retryable 503** so the mobile offline queue keeps the screening rather than discarding it.
  - **Two schema findings against my own earlier work**, fixed in `0007` rather than worked around. `0004` gave `persons` **no name at all** — it followed §8.1 and §8.2's column lists literally, and neither lists one — which left §8.2's matching bundle with nothing to match on besides a hashed identity number most artisanal miners will not volunteer, and left a health worker unable to confirm the record is the right person. And `persons` had no provisional flag, so §8.2 part four had nowhere to record itself. Both added; `docs/IMPLEMENTATION_PLAN.md` §12 items 16–19 record these and two consequences.
  - **Encrypting the name at rest makes fuzzy matching impossible, and §8.2 asks for both.** Edit distance cannot be computed on a hash. The answer: narrow the register deterministically on indexed hashes and on demographics-plus-site, then decrypt only that handful of rows and compare in memory. A phonetic key would allow indexed fuzzy matching and was rejected — Soundex-family algorithms are tuned for English and produce confident nonsense on Shona and Ndebele names, and a confident wrong candidate is worse than none. **§16.2 should say the narrowing step exists**, because it is what makes the two requirements compatible.
  - **Why the scoring weights are safe to pick in code**: no score causes a merge. A score decides only whether a human is asked to look at a pair. Too low and a reviewer sees noise; too high and a duplicate survives until somebody notices — neither mixes two histories, which is the only outcome that cannot be undone. **If a future change ever lets a score merge automatically, these weights stop being engineering and become a clinical decision** (§12 item 18).
  - **API contract change, announced here**: six routes under `/api/v2/persons`, documented in `docs/API_CONTRACT.md`. `POST /resolve` is unauthenticated on the same precedent as the screening path and **returns no name and no number** — a candidate is identified by participant code. - **The screening pipeline runs end to end** (1 November 2026, branch `be/screening-v2`, items 1.5 and 1.10). `POST /api/v2/screenings` executes §10.3 steps 1 to 10 in order: identity resolved through any merge → consent as a hard gate → the active approved instrument → **answers committed before any scoring** → per-condition score → deterioration → safety overrides last → one result row per condition with full provenance → text selected from the content store → a referral keyed to the *result* with a window read from the instrument. Step 11's sending is the only part not built, and the reasons are structural rather than unfinished work.
  - **Three properties separate this from the v1 route, and each is tested.** A scoring failure **keeps the answers** — an incomplete instrument returns `400` with `answers_saved: true` and the session id, where `routers/screening.py` *deletes* the screening when its model call fails. A retry **writes nothing** — `client_session_uuid` is checked before anything else runs, which is the structural fix for the 23 August incident where eighteen duplicate rows accumulated for one miner. And **no model is on this path**, by construction and by an import-graph test, which satisfies §7 step 2: the v2 route is deterministic from its first commit.
  - **A replay reads the stored rows rather than re-classifying**, and the reason is subtler than caching: the instrument can be superseded between the first submission and the retry, and a retry must return what the worker was actually told, not what the current rules would say. A test supersedes the instrument between two submissions of the same key and asserts the reported version does not move.
  - **A referral belongs to a result, not a session** (§10.4, item 1.10). A session produces one result per condition and a referral is always for a particular condition at a particular tier, so a worker flagged for two conditions gets two referrals with two deadlines rather than one row whose meaning depends on which result you read it against. Confirmed on real PostgreSQL: a RED profile against the two-condition fixture produced two referral codes.
  - **The referral window now comes from the instrument**, not from code. §12.2 item 8: the v1 path hardcodes 48 hours for RED and 14 days for ORANGE in `services/referrals.py:17`, numbers that appear in no approved document. `referral_window()` reads `instrument_intervals` and **raises when the Clinical Lead has not stated one** — a deadline is a clinical instruction with a number on it, so an absent number is a missing instruction rather than a reason to pick one. A test strips the intervals and asserts the refusal, and that the answers and results still stand.
  - **Closing a referral captures the outcome, not merely attendance** (`POST /api/v2/referrals/{code}/close`). §10.4's own addition, and the whole Section 9 roadmap depends on it: without the radiological or clinical finding the pilot produces an operational result and no labelled dataset; with it every completed referral is a training example nobody else in the country holds. Five values, closed — free text is easier to fill in and produces nothing a model can learn from. `GET /api/v2/referrals/outcomes/vocabulary` serves the set so the facility page cannot drift out of step with what the database accepts.

A facility reading the pre-alert knows what to look for rather than receiving a bare instruction to investigate, and an audit can reconstruct the decision.

Also recorded there: the v2 pipeline **never writes `question_text`**, because the wording of a question is a patient-facing string that lives in the content store against a message code (§8.4) and copying it into a clinical row is a second, unreviewed copy of text a worker read; and it never writes `answer_score`, because v2 scores per condition and one score per answer cannot express that — the silicosis-shaped defect §8.1 names, in a different table.

Integrity is enforced in `services/referrals_v2.py`, which refuses to create a referral for a result it cannot read. The fourth time this has decided a DDL choice. Migration `0010` rebuilds the table when the v1 columns go, and the real keys arrive then.

A test proves the selector works by approving a message and watching it appear, so only the words are missing, not the wiring.

- **Roles and the audit log** (1 November 2026, branch `be/authz`, item 1.13). §16.6 puts this in Phase One, before the first real record, because retrofitting authorisation onto a system that has already been read is how a breach gets discovered after the fact. Seven roles with capabilities and scope, an append-only audit trail, hashed passwords, and an end date on the two environment-variable accounts.
  - **The tests that matter are the negative ones.** §10's Phase One requirement is explicit — "negative tests for each role attempting access that must fail" — and every row of §16.3's table has a "cannot see" column. Twenty-two of those are now assertions, drawn from the document's own wording: a national stakeholder cannot read a person, a researcher cannot read a person *or* export and read identifiers, a programme sponsor cannot reach an individual result (§14.4), a facility user cannot read a screening with no referral to them, a village health worker cannot reach national data, and **only an administrator can merge two records**, because a false merge mixes two clinical histories with no way to detect it by inspection.
  - **A role plus a scope, never a role alone.** "Facility user: can see referrals directed to their facility" is not a role, it is a role *and* a facility; a village health worker covers a handful of workings, not one and not all. Creating a scoped role with no scope is **refused** — it passes every capability check and is bounded by nothing. And the scoped-query helpers narrow to **nothing** on a missing scope rather than to everything, which is the whole reason they exist instead of an inline condition: the failure mode of a missing scope must be an empty result, never an unfiltered one.
  - **Deny by default.** A capability a role does not list is refused, including one that does not exist, so a new capability is invisible to every role until somebody grants it deliberately. A deactivated principal holds nothing.
  - **Administrative access is not a licence to read records** (§16.3). The administrator role holds `admin.manage`, `person.merge` and `aggregate.read` — and deliberately **not** `person.read` or `screening.read`. An administrator who needs a worker's record has to be given a clinical role too, which is a decision somebody makes rather than a capability that arrives with the job. `GET /api/v2/audit/persons/{id}` therefore refuses an administrator and allows a village health worker, because checking who has touched a record you are responsible for is not an administrative act.
  - **The audit log is append-only, and that is asserted rather than asserted-to-be.** There is no update and no delete anywhere in `services/audit.py`, proven by an AST walk over the module that rejects any attribute assignment or `.delete()` call — verified by adding `row.action = action` and watching it fail. A log that can be edited afterwards answers nothing, and this is the fourth place where a service-layer guard replaced a trigger, because triggers are PostgreSQL-only and invisible to the SQLite suite (§16.2).
  - **A refused access writes a row, and those are the rows that matter.** A role boundary nobody can show being enforced is indistinguishable, to an auditor, from a role model that does not work. `GET /api/v2/audit/refusals` lists them. The refusal commits on its own session, because a refused request has no transaction to join — and never raises, because a failure to log a refusal must not turn a clean 403 into a 500.
  - **Reading the trail is itself audited.** Not circular pedantry: an audit log nobody's reads are recorded in is a log that can be mined quietly.
  - **No personal data in a log line, checked rather than trusted.** A forbidden-key list rejects a name, a number, an answer or a password in `details`, with eight parameterised cases. A failed-login row records neither the address tried nor the password — an email in a failed-login row is a list of accounts somebody tried.
  - **An audit write cannot fail a clinical write.** `record()` flushes into the caller's transaction, so a screening and its audit row stand or fall together and a screening can never be lost because a log row would not fit.
  - **Passwords are hashed** with `hashlib.scrypt` and a per-user salt, parameters stored in the hash so raising them later does not invalidate existing passwords. Chosen over bcrypt/passlib to avoid a dependency whose version handling has broken more builds than it has protected passwords; scrypt is memory-hard, which is the property that matters. A malformed or absent hash fails closed rather than raising, because an exception in a login path is a different bug with the same cause.
  - **`SECRET_KEY` no longer falls back to `"dev-secret"`.** That default meant a production instance missing the variable signed tokens with a value published in this repository's history — **anyone could mint an administrator token**. It now raises a 503 at signing time. This was a live weakness in `routers/auth.py:29`, not a hypothetical one.
  - **The prototype accounts are self-disarming.** `hospital` and `cimas` authenticate only while the `users` table is empty; the moment a real user exists they stop, and a token already issued to one stops with them — a twelve-hour token must not outlive the account it was issued for. Deliberately not a feature flag: a flag nobody turns off is how a prototype credential reaches production. A deactivated user still counts as a user, so deactivating the last account cannot quietly bring the environment credentials back to life.
  - **A bootstrap deadlock, found by a test and resolved deliberately.** The prototype accounts do not hold `admin.manage`, so nothing could create the first administrator. Three ways out, and the first two are worse: giving the prototype accounts the capability widens the credential this item exists to retire, and letting the route run unauthenticated while the table is empty opens a window in which whoever reaches a fresh instance first owns the system — on a public URL, a window measured in minutes. So the first administrator is created by **`backend/scripts/create_admin.py`**, which needs database access, and the person who can run a command against the production database is already the person who could create an administrator by hand. The password is read from the terminal and never taken as an argument, because an argument lands in shell history and the process table. Exercised against both SQLite and PostgreSQL, including the refusal on a second run.
  - **One API shape changed additively**: `GET /api/auth/me` gained `scope`, `capabilities`, `cannot` (§16.3's own column) and `prototype_account`, so a client renders the boundary from the server's definition rather than from a copy. `email` and `role` are unchanged. One existing test asserted exact equality and was updated.

- **Production outage: the Phase One deploy half-migrated, and two live v1 routes returned 500 for about fifty minutes before anyone looked** (2 November 2026, found by a post-merge verification sweep, branch `be/docs-reaudit`).
  - **What broke.** `GET /api/referrals/lookup/{code}` — the hospital-facing page that confirms attendance, which is the surface that makes referral completion measurable at all — and `GET /api/dashboard/today`, the mobile Home screen's numbers. Both returned 500 to every request. `GET /api/facilities`, `/api/mines`, `/api/workers/{phone}`, `/api/auth/*` and every `/api/v2` route were fine, which is what made the cause legible.
  - **Why.** Production does not run `alembic upgrade head` on deploy; the start command is `uvicorn main:app`. Boot calls `init_db()` → `Base.metadata.create_all()`, which creates a missing **table** and **can never add a missing column to a table that already exists**. So the merge gave production all thirty-five tables and none of the eight new columns on `referrals` or the one on `screening_answers`. Every SQLAlchemy query selecting those two models then failed on "no such column" — and only those two.
  - **This was not visible.** `/api/health` reported `{"status":"ok","database":"up"}` throughout, and both halves were true: the process was serving and the database was answering. The schema simply did not match the code. That is the same class of problem as the 11 September outage, where "the API is down" and "the database is unreachable" were indistinguishable from outside — and the fix is the same shape: make the distinction a field.
  - **The migration CI gate could not have caught it**, which is the part worth sitting with. The gate runs `upgrade head` → `downgrade base` → `upgrade head` on a clean PostgreSQL 16 and a drift check, and it passed on every one of the seven pull requests. It verifies that the migrations are correct. It cannot verify that anything runs them. **A green migration gate and a database nobody migrated are compatible states**, and nothing in the repository said so.
  - **Three fixes, in order of what prevents recurrence.**
    - `render.yaml`'s start command is now `python -m alembic upgrade head && uvicorn ...`, with `&&` rather than `;` on purpose: if the migration fails the server must not start against a schema it cannot use. That is the one place where refusing to boot beats booting degraded, because the alternative is exactly the silent half-migrated state that caused this. **`render.yaml` governs nothing** — it was created through Render's REST API and never Blueprint-synced — so the same command has to be set on the service, and `CLAUDE.md`'s deployment section now says so beside the existing warning.
    - `database.missing_schema()` and `log_schema_drift()`, called from the application lifespan: one `ERROR` line at boot naming every missing table and column and telling the reader to run `alembic upgrade head`. It **reports rather than raises** — rule 7, boot degraded, because a server that will not boot is harder to diagnose than one that says what is wrong.
    - `/api/health` gains a **`schema`** field (`ok` or `drifted`) and `schema_missing`, so the gap is visible from outside in one request. **API response-shape change, announced here**; additive, and both fields are absent when `database` is `down` because there is nothing to compare against. Served from the boot-time check rather than recomputed per request: this endpoint is also what wakes a sleeping free-tier instance, and inspecting thirty-five tables on every call would make it slow for no benefit, since drift only changes when a migration runs. **`?recheck=1`** forces a fresh look, which is what you want immediately after running one.
  - **Reproduced before being believed.** A database stopped at migration `0008`, booted through the real application: `/api/health` returned `schema: "drifted"` naming all nine missing columns across both tables — `init_db()`'s `create_all()` having run at that boot and changed nothing, which is the whole point. Eleven tests cover it, including one asserting that **`create_all()` does not repair a missing column**, so nobody has to rediscover why the outage was possible.
  - **Two mistakes of my own worth recording.** The first test file pointed at a dead PostgreSQL address to prove the detector never raises, which made psycopg retry and the file take over two minutes — the identical mistake `test_db_outage.py` already fixed once with a fake engine, now fixed the same way here. And the first version dropped columns with `ALTER TABLE ... DROP COLUMN`, which SQLite refuses on an indexed column; rebuilding the table without them is both engine-portable and closer to the real failure, since production's `referrals` was *created* without those columns rather than having them removed.
  - **Still outstanding, and needing a decision rather than code**: production is still half-migrated, so those two routes are still down. The fix is `alembic upgrade head` against the production database — the migrations are additive and were each verified forward and backward on PostgreSQL 16 — but it is a production change, there is no staging to rehearse on (Phase Zero 0.5), and it is not mine to run unasked.
  - Separately confirmed in the same sweep: **`SECRET_KEY` is set on the service**, so removing its `"dev-secret"` fallback did not break dashboard login — the risk that change carried. And **`IDENTITY_HMAC_KEY` and `CONTACT_ENCRYPTION_KEY` are not set**, so `/api/v2/persons/resolve` and `/api/v2/screenings` return the designed retryable 503 with nothing saved. That is the loud failure the no-default decision was for, working as intended, and two environment variables away from being ready.
  - **The obvious fix would have failed, which is why it was rehearsed first.** `alembic upgrade head` against production does **not** work in this state: it tries to run `0004`, which creates the tables `create_all()` already made, and stops at `DuplicateTable: relation "consent_texts" already exists` with nothing applied. Verified by reproducing production exactly on real PostgreSQL 16 — migrate to `f5bebe94f599`, boot the application so `create_all()` runs, confirm the same nine missing columns across the same two tables — and then watching the naive command fail. **The recommendation in the first report of this incident was wrong and is corrected here**; the working sequence is now a runbook in `docs/STACK.md` rather than a line in a chat message.
  - **The sequence that works, and why each step is safe.** `alembic stamp 0008_consent_text_uniqueness` records what `create_all()` already built, which is true for every table it created from the current models; `alembic upgrade 0009_v2_referrals` is the only migration whose work is genuinely missing, because `referrals` and `screening_answers` pre-existed so `create_all()` left them alone; `alembic stamp head` covers `0010`, whose two tables `create_all()` also made. Verified afterwards by `missing_schema()` reporting nothing, **Alembic's own autogenerate check reporting no drift** — which is what confirms the stamps rather than trusting them — and both broken routes answering again, the referral lookup returning 404 for an unknown code instead of 500.
  - **A stamp past work that is not already present would be worse than the outage**, and the runbook says so: it would leave a database Alembic believes is current and is not, so the next deploy would skip the repair silently. The precondition for the whole procedure is stated first, and `/api/health?recheck=1` is how to check it.
  - **The sanctioned alternative is recorded rather than taken.** §8.1 and `ARCHITECTURE.md` decision 1 say demonstration data is reseeded, not migrated, so dropping every table, migrating an empty database and reseeding would leave a clean history with no stamps in it — a better story for the ethics submission's data-flow description. It also destroys demonstration rows the team has been demoing against, which had grown to real use by late September. Preferred once staging exists and the demonstration target is not also production.

- **Production repaired, and the cause closed** (2 November 2026, authorised and carried out). The outage recorded above is over: `GET /api/dashboard/today` returns 200, `GET /api/referrals/lookup/{code}` returns 404 for an unknown code rather than 500, and `GET /api/health?recheck=1` reports `schema: "ok"`.
  - **Production was worse than the rehearsal, and only the drift check found it.** The first pass repaired `referrals` and `screening_answers` exactly as predicted — at which point `missing_schema()` reported clean for those two tables and both visibly broken routes started working. `alembic check` then revealed that `persons` was missing migration `0007`'s four columns and `consent_texts` its two indexes, because **those tables had been created by an earlier deploy** (after #37) when the models did not yet have them, and every later `create_all()` saw the tables already existed and left them alone. The same bug one layer deeper, from two deploys rather than one. A second pass stamped back to `0006`, ran `0007` and `0008`, and stamped forward; the check is now silent and `missing_schema()` reports nothing.
  - **The runbook in `docs/STACK.md` was wrong by omission and is corrected.** Step 4 is a **loop condition**, not a formality: the drift can be layered because each deploy's `create_all()` froze whatever the models looked like at that moment, so the procedure is stamp → upgrade → stamp → check, **repeated until the check is silent**. Had the first pass been treated as done — which the working routes and a clean `missing_schema()` for two tables both invited — production would have been left with four missing columns on `persons` and the identity routes would have failed the moment they were enabled.
  - **The cause is closed at the service, not just in the file.** The Render service's start command is now `python -m alembic upgrade head && uvicorn main:app --host 0.0.0.0 --port $PORT`, set through Render's REST API — because `render.yaml` records the intent and governs nothing. `&&` rather than `;`, so a failed migration stops the boot instead of serving a schema it cannot use.
  - **All seven CI gates are now required status checks on `main`**, up from four. Clinical specifications, Content strings and Instrument regression suite previously ran without blocking a merge, so a pull request with a broken instrument or an over-budget string could land with a red tick beside it. Sequenced after the stack merged, because a required check a pull request has never run makes that pull request unmergeable.
  - **`IDENTITY_HMAC_KEY` and `CONTACT_ENCRYPTION_KEY` are set on the service.** Generated fresh, which is safe only because the v2 identity routes had never worked in production, so nothing was stored under an earlier key — **after real data exists, losing these keys makes that data unrecoverable**, and they belong in the password manager alongside the rest. The values were deliberately not printed into a transcript; they are readable from the Render dashboard.
  - **Six branches deleted**, with two things worth recording. `be/identity` still carried the superseded commits that had the development keys in them — the ones that failed the secret scan and caused the #40 → #41 replacement; its tree was verified identical to the version on `main` before deleting, so nothing was lost and no ref points at that key material any more. And **the runbook commit had never reached `main`**: #48 merged seconds before it was pushed, so `main` carried the outage fix and the drift detection but not the procedure for recovering a database already in that state. Opened as its own pull request.
  - **A probe that would have written to production was caught before it ran.** The first verification loop posted a real identity bundle to `POST /api/v2/persons/resolve`, which on success creates a person, a participant code and a contact row. Replaced with an intentionally invalid bundle, which exercises the same key check and writes nothing: `503` means the keys are missing, `400` means they are loaded.
  - **The identity routes needed a deploy after the keys, not just the keys.** Render injects environment variables at container start, and the deploy that the first variable triggered had already begun before the second was written, so the live process saw neither. An explicit redeploy was triggered — which is also the first real exercise of the new migration-first start command.
